# RustFS как хранилище контента с правами организации и воркспейса

**Статус:** шаги 0–5 сделаны 9 октября 2026. У каждой организации свой бакет, у воркспейса свой ключ. Перенос уже лежащих файлов запускает оператор; локальные копии снимаются отдельным подтверждением. Уборка снимает объекты без строки старше суток и показывает расхождение бакета с библиотекой.  
**Дата:** 9 октября 2026.  
**Рядом:** [`multi-tenancy-design.md`](multi-tenancy-design.md) (организация → воркспейс → контент), [`scale-out-design.md`](scale-out-design.md) §6a (байты реплики и `/uploads/content`), [`operations.md`](operations.md).

Документ отвечает на вопрос: как перенести файлы библиотеки в [RustFS](https://docs.rustfs.com/) так, чтобы чужая организация и чужой воркспейс не могли прочитать или перезаписать байты, и чтобы экраны, слайды и реплики продолжили играть то, что играют сейчас.

---

## 1. Решение коротко

1. **Herald остаётся единственным местом, где решается «этот человек / этот экран имеет право».** Роли из `docs/multi-tenancy-design.md` (`platform_admin`, `org_owner`, `org_admin`, `workspace_admin`, `workspace_editor`, `workspace_viewer`) не переезжают в консоль RustFS. Оператор по-прежнему входит в дашборд, а не получает ключ S3.
2. **RustFS — закрытый диск с собственной границей.** Анонимной политики бакета нет. Корень (`RUSTFS_ACCESS_KEY` / `RUSTFS_SECRET_KEY`) используется один раз при установке и в рантайме запросов не участвует.
3. **Один бакет на организацию, префикс на воркспейс.** Квота RustFS вешается на бакет и совпадает с лимитом тарифа организации. Внутри бакета IAM-пользователь воркспейса видит только свой префикс.
4. **Плееры, песочные iframe слайдов и реплики ходят в Herald, не в RustFS.** Публичный контракт URL остаётся `/uploads/content/<basename>`. Меняется только то, откуда Herald читает байты и каким ключом.
5. **Локальный каталог `uploads/content` остаётся режимом по умолчанию**, пока RustFS не включён явно. Существующая установка без новых переменных окружения работает как сегодня.

Физическое размещение байт и проверка роли — разные контуры. Первый не подменяет второй: у экрана нет учётной записи IAM, а у слайда в песочнице нет заголовка `Authorization`.

## 2. Что такое RustFS и чего от него ждать

RustFS — S3-совместимое объектное хранилище на Rust, лицензия Apache-2.0. Для этого плана существенны свойства, которые документация на 9 октября 2026 года описывает как рабочие:

| Свойство | Зачем оно здесь |
|---|---|
| SigV4, path-style (`forcePathStyle: true`) | Клиент — AWS SDK for JavaScript v3, отдельный протокол не пишем |
| IAM: пользователи, группы, свои политики, явный Deny | Граница префикса воркспейса |
| Политика бакета, Public Access Block | Запрет анонимного чтения |
| STS `AssumeRole`, сервисные аккаунты, срок жизни ключа | Позже, для коротких операций; в первой поставке не обязательны |
| Жёсткая квота бакета в байтах | Потолок организации. Запись сверх квоты — `InvalidRequest` / `Bucket quota exceeded` |
| Presigned GET и PUT | Запасной прямой канал для больших роликов, не основной путь плеера |
| Multipart, Range, условные запросы, пользовательские метаданные, теги | Докачка, перемотка видео, сверка sha256 |
| Lifecycle по префиксу | Срок жизни недокачанных multipart и, если включим версии, старых версий |
| SSE-S3 | Шифрование на диске. Требует настроенный KMS; без него запись с шифрованием падает |
| Версионирование и Object Lock | Есть. Для библиотеки вывесок по умолчанию **выключены**: замена ролика плодит версии, а Lock мешает удалению кампании |

Ограничения, которые план учитывает, а не обходит:

- **Квота только на бакет, не на префикс.** Поэтому бакет = организация. Лимит одного клиента реселлера внутри организации считает Herald (`SUM(file_size)`), RustFS его не умеет.
- **Если проверка квоты не смогла прочитать свою конфигурацию, RustFS пишет `Bucket quota check degraded to allow` и запись пропускает.** Квота — второй замок. Первый — проверка в Herald до `PutObject`. За предупреждением нужен мониторинг.
- **ACL намеренно не поддерживаются.** Права задаются политиками IAM и политикой бакета.
- **Одноузловой режим (SNSD) без erasure coding.** Годится для пробы и маленького self-host. Боевой кластер — несколько узлов и дисков, TLS, свои бэкапы. Образ в примерах документации Tenant — `rustfs/rustfs:1.0.0-beta.10`; в compose пиновать конкретный тег после стенда, не `latest`.
- **Часть команд `rc` возвращает `not implemented`** (в документации 0.1.29 это, среди прочего, создание бакета с Lock через CLI и удаление конкретной версии через `rc object remove --versions`). Администрирование закладывать на S3 API и те операции `rc`, которые на стенде реально выполняются. Совместимость с `mc admin` не считать заданной.
- **Kubernetes Tenant** (отдельный кластер на команду) для docker-compose self-host избыточен. Один кластер RustFS на инсталляцию Herald, изоляция — бакеты и префиксы. Отдельный Tenant имеет смысл только если хостинг когда-нибудь вынесет хранилище в Kubernetes и захочет железную изоляцию крупного заказчика.

## 3. Как байты живут сейчас

На первичной ноде файл лежит в `$DATA_DIR/uploads/content/<filepath>`:

- обычная загрузка — `<uuid>.<ext>`;
- файл, пришедший по mesh, — `<sha256>.<ext>`, и один файл на диске может держать строку `content` в каждом воркспейсе.

Колонки `content.filepath`, `content.thumbnail_path`, `content.subtitle_url` хранят имя файла. `file_size` и `byte_digest` описывают байты. Каталог создаётся из `UPLOADS_DIR` / `DATA_DIR` (`server/config.js`). Образ Docker монтирует всё состояние, включая эти файлы, в том `/data` (`Dockerfile`, `docker-compose.yml`).

Кто читает:

| Вход | Кто | Проверка |
|---|---|---|
| `GET /uploads/content/<basename>` | плеер, слайд, дашборд | Файла достаточно. Каталог статический (`server/server.js`, `express.static`). Заголовки: CORS `*`, кэш 30 дней `immutable`, `hardenUploadResponse` (CSP sandbox, чужие расширения — как скачивание). Промаха — JSON 404, чтобы плеер не закэшировал HTML дашборда как ролик |
| `GET /api/content/:id/file` | плеер и виджет без сессии, если id есть в плейлисте или виджете того же воркспейса; иначе сессия с членством | `requesterCanAccessContent` |
| Дашборд `GET /api/content` | сессия | Строки только своего `workspace_id` плюс платформенные `workspace_id IS NULL` |
| Реплика scale-out | fetch-through на `PRIMARY_URL/uploads/content/<name>` | Кэш C3 кладёт байты в свой `uploads/content` (`docs/scale-out-design.md` §6a) |

Удаление не делает `unlink`, пока другой ряд указывает на то же имя (`server/lib/content-files.js`). Это прямое следствие общего каталога: удаление копии одного заказчика не должно стереть файл другого.

Лимит тарифа считается как `SUM(file_size)` по всем воркспейсам организации (`server/middleware/subscription.js`, `checkStorageLimit`, шаг 0). Живой тариф — план владельца организации (`users.plan_id`, его пишет Stripe); колонка `organizations.plan_id` при создании копируется и дальше не обновляется, поэтому квота на неё не опирается. Для бакета «одна организация» цифра Herald и квота RustFS смогут совпасть.

Временные вещи остаются на локальном диске и в RustFS не кладутся: куски докачиваемой загрузки, разбор HTML-бандла, кадр для ffmpeg/ffprobe, прокси-кэш `proxy-cache`, шрифты `/fonts` и `/fonts/u`. Шрифт слайду нужен с CORS и без `Content-Disposition: attachment`; это не библиотека контента.

Платформенные строки `content.workspace_id IS NULL` (общие шаблоны) не принадлежат ни одной организации.

## 4. Что означает «права по воркспейсу и организации»

Три разные двери. Их легко склеить в одну и получить дыру.

### 4.1 Оператор в дашборде

Уже решено в Herald: членство в воркспейсе и роль. RustFS это повторяет вторым контуром. Запрос на чтение или запись идёт ключом, у которого в политике только префикс этого воркспейса. Ошибка в SQL, которая подставила чужой `workspace_id`, упирается в `AccessDenied` на объекте.

Соответствие ролей и действий S3 (ресурс — префикс воркспейса, для организации — весь бакет):

| Роль Herald | Действия RustFS |
|---|---|
| `workspace_viewer` | `s3:GetObject`, `s3:GetBucketLocation`, `s3:ListBucket` с условием `s3:prefix` |
| `workspace_editor`, `workspace_admin` | то же плюс `PutObject`, `DeleteObject`, `AbortMultipartUpload`, multipart |
| `org_admin`, `org_owner` | те же действия на все префиксы бакета организации. Удаление бакета — только `org_owner`, отдельным административным ключом, не ключом данных |
| `platform_admin` | не постоянный житель бакета заказчика. Операции поддержки идут сессией Herald, которая выбирает ключ воркспейса, в который вошли. Отдельный ключ платформы нужен для бакета шаблонов и для создания бакетов |
| экран, API-токен устройства | ключа RustFS нет |

`ListBucket` без условия на префикс перечисляет всю организацию. В политике воркспейса условие обязательно. Встроенная политика RustFS `readonly` не включает `ListBucket`; свою политику пишем явно, готовые `readwrite` / `consoleAdmin` на тенантов не вешаем.

### 4.2 Экран и слайд

Экран играет URL из снимка плейлиста. Слайд рисуется в iframe с `sandbox` без `allow-same-origin`: документ в непрозрачном origin, cookie дашборда туда не приезжают, заголовок `Authorization` на `<img>` и `<video>` не поставить. То же ограничение уже записано у шрифтов и у `/uploads/content` в `server/server.js`.

Поэтому плеер не логинится в RustFS. Право экрана устроено так:

- в плейлист, снимок и HTML слайда попадает только тот basename, который сервер выдал после проверки воркспейса;
- RustFS этот basename не принимает от сети: снаружи открыт только Herald;
- Herald по basename находит строку `content` и читает объект ключом её воркспейса.

Кто узнал basename, может попросить байты у Herald. Так устроено и сегодня: каталог публичный, имя — uuid или sha256. Этот план не обещает закрыть capability-URL без смены всех плееров. Он обещает, что угадывание имени больше не читает диск напрямую и что ключ одного воркспейса не открывает соседний префикс.

Усиление capability-URL (подпись в query, заголовок device token на каждом плеере) — отдельная поставка после parity. Подпись в query меняет ключ кэша: `server/lib/player-cache-policy.js` и тесты уже отличают `/uploads/content/clip.mp4?rev=100` от `?rev=200`. Вращающийся токен в query сбросит офлайн-кэш панелей. Пока контракт пути стабильный, панели не перекачивают библиотеку.

### 4.3 Соседние воркспейсы одной организации

Реселлер видит клиентов как разные воркспейсы одной организации (`docs/multi-tenancy-design.md`). Копирование макета клиенту — осознанное действие `org_admin`: `CopyObject` из одного префикса в другой ключом организации, новая строка `content` в целевом воркспейсе. Общего файла на двоих больше нет.

Сегодня mesh как раз хранит один sha256-файл на много воркспейсов. Это экономит диск и ломает границу: удаление завязано на счётчик ссылок, а байты физически общие. В раскладке по префиксам каждая строка владеет своим объектом. `CopyObject` внутри кластера дёшев по сети, но место считается дважды — и квота организации это увидит. Так и должно быть: два клиента, два объёма.

Платформенный шаблон (`workspace_id IS NULL`) живёт в бакете `herald-platform`. Ключ воркспейса его не пишет. Раздаёт его Herald ключом платформы, тем же URL `/uploads/content/...`.

## 5. Раскладка бакетов и ключей

Имена бакетов — DNS-совместимые, без данных заказчика сверх id:

| Бакет | Содержимое |
|---|---|
| `herald-org-<organizationId>` | контент, миниатюры, субтитры, постеры воркспейсов этой организации |
| `herald-platform` | строки с `workspace_id IS NULL` |
| `herald-scratch` | не используем. Недокачанное и сырое до проверки MIME остаётся на локальном диске инстанса |

Префикс воркспейса:

```
ws/<workspaceId>/c/<contentId>/original
ws/<workspaceId>/c/<contentId>/thumb
ws/<workspaceId>/c/<contentId>/subs
```

`contentId` в ключе, а не sha256. Замена файла пишет новый объект (новый id или суффикс поколения — см. ниже) и снимает старый, когда на него никто не ссылается. Расширение и исходное имя в ключе не кодируются: они бывают с пробелами и Unicode, а плеер их не видит. Их место — метаданные объекта и колонки строки.

Метаданные объекта (и теги, чтобы квоту и уборку можно было сверить без SQLite):

- `Content-Type` — тип после sniff, тот же, что в `content.mime_type`;
- `x-amz-meta-herald-sha256` — `byte_digest`;
- `x-amz-meta-herald-workspace` — id воркспейса;
- `x-amz-meta-herald-content` — id строки;
- тег `herald-role=original|thumb|subs`.

Политика воркспейса, по смыслу:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject", "s3:AbortMultipartUpload"],
      "Resource": "arn:aws:s3:::herald-org-ORG/ws/WS/*"
    },
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:GetBucketLocation"],
      "Resource": "arn:aws:s3:::herald-org-ORG",
      "Condition": { "StringLike": { "s3:prefix": ["ws/WS/*"] } }
    }
  ]
}
```

У `workspace_viewer` в первом списке только `s3:GetObject`. Явный `Deny` на `ws/*` чужих воркспейсов не нужен, пока нет `Allow` шире префикса: несовпавшая политика в RustFS — отказ.

Публичная политика бакета с `"Principal": "*"` не ставится. Public Access Block с `BlockPublicPolicy` оставляем включённым.

Замена ролика сегодня пишет новый basename и отвязывает старый (`replace` в `server/routes/content.js`). Ключ объекта ведёт себя так же: новый объект, строка обновляет `storage_key`, старый ключ удаляется по правилу «никто не ссылается». Поле `filepath` (basename в URL) при замене тоже меняется, как сейчас, чтобы `immutable` на 30 дней не отдал панели старые байты по старому пути.

Версионирование бакета не включаем. История кампании уже есть в ревизиях Herald (`server/lib/revisions.js`), а версии объектов удвоят занятое место и усложнят удаление. Если позже понадобится восстановление «стёрли бакет», это бэкап тома RustFS и снимок SQLite, а не Object Lock.

## 6. Кто какой ключ держит

Долгоживущие секреты:

| Секрет | Где лежит | Для чего |
|---|---|---|
| Корень RustFS | env на хосте RustFS, не в образе Herald и не в git | первый запуск, сломанный IAM |
| `herald-provisioner` | env Herald (`RUSTFS_PROVISIONER_ACCESS_KEY` / `SECRET`) | создать бакет, квоту, политика, пользователь. В `GetObject`/`PutObject` не используется |
| Ключ воркспейса и ключ организации | SQLite, секрет зашифрован | чтение и запись байт этого scope |
| Ключ `herald-platform` | env Herald | только бакет шаблонов |

Секрет тенанта шифруется ключом `STORAGE_SEAL_KEY` (файл в `$DATA_DIR/certs`, рядом с JWT, тот же режим «если нет — создать при первом включении бэкенда»). В логи, activity и ответы API ключ не попадает. Расшифровка в памяти процесса на время запроса.

Создание воркспейса (лениво, на первой загрузке файла, и повторно идемпотентно):

1. Бакет организации есть. Если нет — создать, включить Block Public Policy, выставить квоту из тарифа (`max_storage_mb`, `-1` = квоту не ставить).
2. Пользователь `ws-<workspaceId>` с политикой префикса. Пользователь `org-<organizationId>` с политикой на бакет.
3. Строки в новой таблице учёта (ниже). Повторный вызов видит пользователя и не крутит секрет заново.

Удаление воркспейса: после того как Herald удалил строки и объекты префикса, пользователь IAM снимается. Удаление организации (`org_owner`): снять квоту не нужно, удалить бакет, когда листинг пуст. Чужие бакеты ключ организации не видит, потому что его политика указывает на один ARN.

Один общий ключ приложения на все воркспейсы этот план не считает реализацией прав. Он годится только как временный стенд «байты вообще читаются». В поставке, которую можно включать клиентам, на запросе данных стоит ключ scope.

Кэш клиентов S3 в процессе: по id воркспейса, с бросанием после смены ключа. Ключ организации кэшируется отдельно и не подставляется в запрос редактора воркспейса.

## 7. Как идут байты

Новый модуль `server/lib/storage/` с двумя адаптерами: `fs` (сегодняшнее поведение) и `s3`. Выбор — `CONTENT_BACKEND=fs|s3`, по умолчанию `fs`. Маршруты не собирают путь `path.join(contentDir, basename)` сами; они просят модуль. Пока бэкенд `fs`, наблюдаемое поведение, тесты и реплика не меняются.

Операции модуля: `put`, `getStream` (с Range), `head`, `deleteIfUnreferenced`, `copy`, `presignGet` (не вызывается в первой поставке).

Шаг 1 ввёл каталог `server/lib/storage/` и адаптер `fs`. `put`, `getStream`, `head`, `copy` и удаление локальных байт идут через него; `deleteIfUnreferenced` считает ссылки в `lib/content-files.js` и снимает файл тем же адаптером. `presignGet` нет. Пустой `CONTENT_BACKEND` и `fs` оставляют `/uploads/content` как `express.static`, а `/api/content/:id/file` — как `sendFile`.

Шаг 2 добавил адаптер `s3` и path-style SigV4. Ключ объекта — `ws/<workspaceId>/c/<contentId>/original|thumb|subs`, платформенная строка — `platform/c/<contentId>/...`. Локальный файл после `PutObject` остаётся; шаг 4 снимает его отдельным подтверждением. Пока бэкенд `s3` и это первичная нода, чтение идёт в бакет и, если объекта ещё нет, в локальный файл. Реплика с `PRIMARY_URL` бакет не читает. Неполное окружение `s3` и любое другое значение `CONTENT_BACKEND` останавливают процесс при загрузке модуля.

Шаг 3 заменяет один ключ стенда. `RUSTFS_ACCESS_KEY` остаётся ключом контейнера RustFS и в `GetObject` / `PutObject` Herald не участвует. Бакет организации — `herald-org-<organizationId>`, шаблоны — `herald-platform`. Пользователь `ws-<workspaceId>` видит только свой префикс, пользователь `org-<organizationId>` видит бакет и не может его удалить. Секрет в `storage_principals.secret_enc` закрыт `STORAGE_SEAL_KEY`. Копирование между воркспейсами одной организации — `copyWithinOrganization`, его не вызывает загрузка.

Шаг 4 не включает перенос сам. Оператор запускает его на карточке системы (платформенный администратор). Процесс берёт одну строку, сверяет размер и sha256, кладёт объект и только потом пишет `storage_key`. Повтор пропускает строку с живым `HeadObject`; если объекта нет, строка кладётся снова. Чтение: пустой `storage_key` — диск, без запроса в бакет; заполненный — бакет, затем диск, если объекта нет. Реплика бакет не читает и локальные копии не снимает. Удаление локальной копии — отдельное подтверждение `drop-local-copies`, и только для имени, у которого у каждой строки есть ключ и живой объект. `/api/status` показывает числа и последнюю ошибку без путей и секретов, и только когда бэкенд `s3`. На `fs` этого блока нет.

### 7.1 Загрузка

Порядок, который нельзя переставлять:

1. Приём во временный файл на диске инстанса (как multer сейчас). В бакет сырое тело не пишется: sniff, бандл и отказ по лимиту должны уметь выкинуть байты, не оставив объект.
2. `checkStorageLimit` по сумме организации (после сдвига учёта) и по остатку квоты, если бэкенд `s3` умеет спросить usage. Отказ — до `PutObject`.
3. Sniff MIME, бандл, ffmpeg — по локальному временному файлу. Миниатюра тоже локальный файл.
4. `PutObject` ключом воркспейса: сначала оригинал, потом миниатюра. В метаданные — sha256, посчитанный тем же `digestFile`, что пишет `byte_digest`.
5. `INSERT` строки. `filepath` по-прежнему basename для URL. Новые колонки `storage_bucket`, `storage_key` указывают на объект. `thumbnail_path` остаётся basename; ключ миниатюры выводится из `storage_key` суффиксом `/thumb` либо хранится рядом, если так проще не сломать рефкаунт.
6. Временные файлы удаляются. Если `PutObject` прошёл, а `INSERT` нет — объект удаляется тем же ключом (компенсация). Если `INSERT` прошёл, а миниатюра нет — строка живёт без миниатюры, как сегодняшние ролики без ffmpeg.

Докачиваемая загрузка (`server/lib/upload-session.js`) собирает части локально и вызывает тот же шаг 4 на finalize. В scratch-бакет части не кладём: проще сохранить текущий сборщик, чем тащить multipart-сессию S3 в контракт браузера.

### 7.2 Чтение

`GET /uploads/content/<basename>` перестаёт быть `express.static` в режиме `s3` (в режиме `fs` монтирование то же). Обработчик:

1. Ищет строку по basename (`filepath`, `thumbnail_path` или `subtitle_url`). Нет строки — JSON 404 без `Cache-Control: immutable`, как промах сейчас.
2. Берёт ключ воркспейса строки (или ключ платформы, если `workspace_id IS NULL`).
3. Проксирует `GetObject`, пробрасывая `Range`, чтобы перемотка видео не качала файл целиком через память.
4. Ставит те же заголовки, что `hardenUploadResponse` и текущий mount: CORS, CORP, CSP sandbox, кэш 30 дней только если объект найден, `Content-Type` из строки, а не «как решит S3».

`GET /api/content/:id/file` и миниатюра идут в тот же прокси после уже существующей проверки плейлиста / виджета / членства. Два места отдачи файла остаются двумя URL, но одно чтение байт.

Реплика C3 в этом плане не начинает писать в общий RustFS. Она по-прежнему качает `PRIMARY_URL/uploads/content/<name>`, кладёт файл в свой каталог и отдаёт его локально. Иначе реплика получила бы сеть до бакета первичной ноды и второй писатель в тот же префикс. Общий бакет на несколько нод Herald — отдельное решение, его здесь нет.

Прямой presigned GET до плеера не делаем в первой поставке. Подпись привязана к хосту, схеме и порту; панель за NAT, смена `RUSTFS_PUBLIC_ENDPOINT` и песочница слайда ломают это быстрее, чем прокси. Presign остаётся функцией модуля для следующей поставки (большой файл мимо процесса Node), с тем же стабильным URL Herald: 302 только если плеер умеет и флаг включён. Пока флага нет.

### 7.3 Удаление и замена

Локальный файл снимает `unlinkIfUnreferenced` только когда больше ни одна строка не называет этот basename. Объект строки снимает `forgetContent` по её content id: сосед, который делит имя файла, держит свой объект. Пока перенос не дописал `storage_key` всем строкам этого имени, локальный файл остаётся — его не снимает ни удаление одной строки, ни сам перенос. Снять имя, которое строки ещё называют, может только подтверждение оператора, и только если у каждой такой строки ключ заполнен и `HeadObject` живой.

Возврат `write_bytes_used` на mesh (`releaseMeshProvenance`) остаётся про байты строки, не про физический файл.

Снятие объекта — `DeleteObject` тем ключом, которым писали. Ошибка сети логируется. Уборка сирот идёт ключом организации (для `herald-platform` — ключом платформы, не корнем): объект нашего ключа, чей `content id` нет в SQLite и которому больше суток, снимается. Более молодой объект остаётся, потому что публикация кладёт байты раньше строки.

### 7.4 Mesh, бэкап, импорт

Приём mesh (`server/lib/mesh/content-receive.js`, `content-sync.js`) по-прежнему пишет временный файл, сверяет размер и sha256, затем `put` в префикс воркспейса-получателя. Отправитель отдаёт байты своим URL Herald. Общий sha256-объект на получателе не переиспользуется между воркспейсами.

Бэкап в `server/routes/status.js` по-прежнему обходит каталог файлов и не скачивает объекты из бакета. Пока локальная копия не снята подтверждением, архив с файлами содержит те же байты. После подтверждения файла в архиве нет: в манифесте у такой строки `bytes_in_object_storage`. Снимок SQLite без тома RustFS недостаточен, снимок тома RustFS без SQLite тоже. Восстановление — пара.

## 8. Учёт места

Две цифры, и у каждой свой вопрос.

| Вопрос | Кто отвечает | Что будет, если разойдутся |
|---|---|---|
| Можно ли этому клиенту загрузить ещё | Herald, до приёма тела: сумма `file_size` по организации против `plans.max_storage_mb` | Отказ с тем же `STORAGE_LIMIT`, что сейчас |
| Не съест ли организация диск кластера | Квота бакета RustFS, выставленная тем же числом байт | `Bucket quota exceeded`. Herald показывает ту же ошибку лимита, не сырой XML |

`max_storage_mb = -1` — квоту бакета не ставим.

Квота RustFS при сбое проверки пропускает запись. Поэтому отказ по тарифу нельзя переносить «пусть бакет сам». После загрузки Herald всё равно хранит `file_size`: это цифра интерфейса и mesh-allowance.

Сдвиг с `user_id` на организацию сделан в шаге 0: сумма по всем `content.workspace_id`, чьи воркспейсы входят в организацию. Поддержка без `users` внутри воркспейса берёт потолок этой организации, а не безлимит. Строка с пустым `user_id` входит в сумму организации сессии и ни в какую другую: это не второй заказчик и не чужой воркспейс. Платформенная строка без `workspace_id` не входит никуда. Общий файл на диске (одно имя у двух строк) считается дважды — по `file_size` каждой строки.

Лимит одного воркспейса внутри организации RustFS не выражает. Если реселлеру нужна квота «клиенту 5 ГБ», это колонка на `workspaces` и проверка в Herald. В этот план она не входит, пока её нет в тарифе.

При удалении байты квоты освобождаются самим RustFS (квота считает текущие объекты). У Herald цифра тоже должна уменьшаться: она и так равна сумме живых строк.

## 9. Схема

К строке `content`:

```sql
ALTER TABLE content ADD COLUMN storage_bucket TEXT;  -- NULL = байты ещё на локальном диске
ALTER TABLE content ADD COLUMN storage_key TEXT;
```

`NULL` в обоих полях — законное состояние на всё время миграции и навсегда для `CONTENT_BACKEND=fs`.

Учёт ключей, без секрета в открытом виде:

```sql
CREATE TABLE storage_principals (
    id              TEXT PRIMARY KEY,
    scope           TEXT NOT NULL,          -- 'organization' | 'workspace' | 'platform'
    organization_id TEXT,
    workspace_id    TEXT,
    bucket          TEXT NOT NULL,
    access_key_id   TEXT NOT NULL,
    secret_enc      TEXT NOT NULL,          -- шифротекст STORAGE_SEAL_KEY
    created_at      INTEGER NOT NULL
);
```

Уникальность: один principal на воркспейс, один на организацию. Платформенный ключ в эту таблицу можно не класть, он в env.

Индекс по `storage_key` нужен уборке сирот и удалению. Секреты в дампы отладочных логов не попадают: дамп строки principal маскирует `secret_enc`.

## 10. Миграция уже лежащих файлов

Включение `CONTENT_BACKEND=s3` не переписывает каталог само.

Фоновый перенос, по одной строке, с паузой, с идемпотентностью:

1. Выбрать строку с локальным `filepath` и пустым `storage_key`.
2. Прочитать файл, сверить размер с `file_size` и sha256 с `byte_digest`, если дайджест есть. Нет файла — строку не трогать, записать ошибку в статус, не выдумывать объект.
3. `PutObject` в префикс её воркспейса. Общие sha256-файлы: каждая строка получает свой объект, байты читаются с диска один раз и кладутся N раз.
4. `HeadObject`, сверить размер и метаданный sha256.
5. Записать `storage_bucket` и `storage_key`.
6. Локальный файл удалить только когда у всех строк с этим basename `storage_key` заполнен. До этой точки `fs` и S3 могут держать копию. Чтение: если `storage_key` есть — из RustFS, иначе с диска. Так обрыв на середине не оставляет строку без байт.

Платформенные строки едут в `herald-platform`.

Откат: `CONTENT_BACKEND=fs` и файлы, которые ещё не удалены с диска, снова раздаются монтированием. Строки, у которых локальный файл уже снят, без RustFS не прочитаются. Поэтому удаление локальной копии — отдельный шаг после того, как выборочное чтение с ноды (плеер, дашборд, Range) прошло. На инсталляции с репликами локальные файлы первичной ноды не снимать, пока реплика не умеет читать ответ нового обработчика (она и так ходит в `/uploads/content/<name>`, так что умеет, как только обработчик отдаёт те же байты).

Повторный запуск переноса пропускает строки с заполненным `storage_key` и живым `HeadObject`. Если ключ есть, а объекта нет, строка кладётся снова, объект не выдумывается при отсутствии локального файла.

Реализовано в шаге 4. Запуск — `POST /api/admin/content-storage/start` (платформенный администратор). Это не флаг удаления. Удаление локальных копий — `POST /api/admin/content-storage/drop-local` с телом `{ "confirm": "drop-local-copies" }`. Прогресс — `content_storage` в `/api/status`, только при `CONTENT_BACKEND=s3`.

## 11. Поставка по шагам

Каждый шаг включается на стенде и не меняет умолчание `fs`.

### Шаг 0. Учёт места по организации — сделано (9 октября 2026)

`checkStorageLimit`, `storageRoomBytes` и резерв незавершённых загрузок суммируют контент организации воркспейса, а не `user_id`. Потолок — `max_storage_mb` плана владельца организации. `SELF_HOSTED` сам по себе потолок не снимает: безлимит остаётся у плана с `max_storage_mb = -1`. Подписка в дашборде показывает эту же сумму и подпись, что место общее для воркспейсов организации.

Проверено тестами: поддержка внутри полного воркспейса получает отказ, поддержка без воркспейса по-прежнему доходит до маршрута, пустой план владельца — `No plan found`, общий sha256-файл считается построчно и только в своей организации, параллельные сессии делят один резерв. Копирование плейлиста при переносе экрана упирается в организацию назначения.

### Шаг 1. Порт хранилища, адаптер `fs` — сделано (9 октября 2026)

Чтение, запись и удаление байт библиотеки идут через `server/lib/storage/`. Корень — тот же `config.contentDir`, имена по-прежнему basename. `/uploads/content`, `/api/content/:id/file`, загрузка, замена, mesh, реплика C3 и бэкап работают с теми же файлами. Новых переменных нет: отсутствующий `CONTENT_BACKEND` значит `fs`. На этом шаге значение `s3` или любое другое останавливало процесс, а не молча писало на диск.

`presignGet` нет — его некому вызывать, пока отдача идёт через Herald. Колонки `storage_bucket` / `storage_key` не добавлялись. `s3` разрешён с шага 2 и только при полном наборе `RUSTFS_*`.

Проверено: адаптер кладёт, читает Range, копирует и удаляет только внутри своего корня; `..` в относительном пути истории отклоняется. Исходная проверка реплики C3 смотрит на `digestFile(storage.file(filepath))` — это тот же `digestFile`, путь теперь спрашивает порт.

### Шаг 2. RustFS рядом и адаптер `s3` на один бакет стенда — сделано (9 октября 2026)

Сервис `rustfs` в `docker-compose.yml` и `docker-compose.example.yml` стоит в профиле `rustfs`. `luminascreen` его не ждёт: обычный `docker compose up` второе хранилище не поднимает. Порт S3 наружу не опубликован, консоль — `127.0.0.1:9001`, том `rustfs-data` отдельный от `st-data`, образ `rustfs/rustfs:1.0.0-beta.10`, пользователь контейнера `10001:10001`. Имена переменных есть в `.env.example`, значений секретов нет.

Адаптер — path-style SigV4 без AWS SDK. `storage.put` / `storage.file` по-прежнему локальный диск: sniff, ffmpeg, история и `open(dir)` туда и пишут, в том числе кэш реплики. В бакет кладётся уже готовый файл: оригинал, миниатюра, субтитры. Загрузка публикует до `INSERT` и снимает объект, если вставка не удалась. Замена черновика на согласование живой объект не перезаписывает; публикация черновика ставит байты в бакет после выпуска. Удаление строки снимает только её `original` / `thumb` / `subs`. Пока имя файла ещё нужно другой строке, локальный unlink по-прежнему считается по basename.

Проверено без живого RustFS: ключ на content id, Range, миниатюра в ключе `thumb`, удаление одной из двух строк оставляет вторую, тело `Bucket quota exceeded` становится `STORAGE_LIMIT`, промах — JSON 404 без `immutable`, на попадании вызывается `hardenUploadResponse` (CSP, nosniff, CORS, CORP). Подпись сверена с примером ключа AWS. `CONTENT_BACKEND=s3` без endpoint не стартует; `fs` без новых переменных не меняется.

### Шаг 3. Ключи по организации и воркспейсу — сделано (9 октября 2026)

Первая запись в воркспейс создаёт бакет организации, включает Block Public Policy и ставит квоту из `max_storage_mb` плана владельца. `-1` квоту снимает. Пользователи IAM `org-<organizationId>` и `ws-<workspaceId>` создаются через admin API RustFS (`/rustfs/admin/v3/`), политика — из §5. Повторный вызов читает зашифрованный секрет и не выпускает новый. Платформенная строка без воркспейса идёт в `herald-platform` ключом `RUSTFS_PLATFORM_*`.

Запись, чтение и удаление байт берут клиент воркспейса. Ключ организации к этому запросу не подставляется: им делается только явное `copyWithinOrganization` и проверка, пуст ли бакет при удалении организации. Загрузка и перенос экрана этот метод не вызывают: перенос по-прежнему делит локальный файл, а объект в бакете копируется только этим вызовом. Квота перечитывается, когда процесс заново открывает организацию (после перезапуска — сразу). Удаление воркспейса снимает его пользователя IAM после попытки удалить объекты. Удаление организации удаляет бакет, когда листинг пуст. Корень (`RUSTFS_ACCESS_KEY`) на этом пути не читается.

В строку `content` пишутся `storage_bucket` и `storage_key`, когда объект уже опубликован и строка есть. `NULL` по-прежнему значит «байты на диске». Перенос старых строк сделан в шаге 4. `presignGet` нет.

Проверено без живого RustFS: политика воркспейса A не пускает `GetObject` префикса B, политика организации пускает оба и не содержит `DeleteBucket`; отправленный документ тот же. `PutObject` подписан ключом `ws-`, копирование — ключом `org-`, загрузка этот метод не вызывает. Чужая организация копирование не проходит. Ответ admin API и текст ошибки не содержат `secretKey`. Печать шифрует секрет так, что в шифротексте его нет. Пустой `CONTENT_BACKEND` по-прежнему диск.

### Шаг 4. Перенос — сделано (9 октября 2026)

Оператор с карточки «Система» запускает перенос. Процесс берёт одну строку с локальным `filepath` и пустым `storage_key`, сверяет размер и sha256, кладёт оригинал (и миниатюру с субтитрами, если файлы есть) в префикс воркспейса и пишет `storage_bucket` / `storage_key` только после `HeadObject`. Платформенная строка идёт в `herald-platform`. Общий basename хешируется один раз за проход и кладётся отдельным объектом на каждую строку. Локальный файл при этом остаётся.

Нет файла, не сходятся размер или sha256 — строка не меняется, объект не создаётся, ошибка попадает в статус. Отказ квоты останавливает проход. Повтор пропускает живой `HeadObject` и заново кладёт строку, если объекта нет. Реплика (`PRIMARY_URL`) перенос не запускает и локальные копии не снимает. Перезапуск продолжает проход, только если оператор его уже включил.

`/api/status` при `s3` отдаёт `content_storage`: сколько строк ещё без ключа, сколько с ключом, идёт ли перенос, последняя ошибка. Путей и секретов там нет. На `fs` блока нет, ответ для проверки живости тот же.

Удаление локальных копий — вторая кнопка. Нужно ввести `drop-local-copies`. Имя снимается только когда у каждой строки с этим именем заполнен `storage_key` и объект читается. Пока перенос идёт, удаление отклоняется. В архиве экспорта после этого у строки без локального файла стоит `bytes_in_object_storage`; объекты в архив не забираются.

Проверено без живого RustFS: успешная строка получает ключ и оставляет файл; повтор с живым `HeadObject` не кладёт объект снова; пропавший объект кладётся снова; две строки одного файла — два объекта и один подсчёт sha256, файл остаётся, пока у одной нет ключа, и снимается подтверждением, когда ключи есть у обеих; промах `HeadObject` файл не снимает; нет файла, чужой размер и чужой sha256 объект не создают; платформенная строка попадает в `herald-platform`; квота останавливает проход и не пишет секрет в статус; `fs` и реплика перенос не начинают. Строка без `storage_key` читается с диска и бакет не открывает.

### Шаг 5. Наблюдаемость и уборка — сделано (9 октября 2026)

Фоновый проход, когда бэкенд `s3` и это не реплика. Один шаг за раз, с паузой. Список и удаление идут ключом организации, для шаблонов — ключом `herald-platform`. Корень RustFS на этом пути не используется.

Объект снимается, только если ключ имеет вид `ws/<workspace>/c/<contentId>/original|thumb|subs` или `platform/c/<contentId>/...`, этого `contentId` нет в `content`, и `LastModified` не моложе суток. Чужой ключ не трогается. Объект моложе суток не трогается: между `PutObject` и `INSERT` строки ещё нет.

Сверка идёт по объектам `original` и `SUM(file_size)` строк, у которых `storage_key` уже заполнен. Миниатюра и субтитры в эту сумму не входят: колонка `file_size` их не считает. Незавершённые `upload_sessions` организации — допуск. Байты сверх этого допуска и строка без объекта — событие в `/api/status` и на карточке системы, не тихий дрейф. Следующий проход, если картина сошлась, событие снимает.

Фраза `Bucket quota check degraded to allow` в заголовке или теле ответа запоминается, пишется в лог один раз и видна оператору. Секрет из того же тела в статус не попадает. Лимит Herald до `PutObject` от этого не отменяется.

`PutObject` ставит тег `herald-content` и `herald-role` вместе с прежними метаданными. Presigned-отдача, версионирование, SSE-S3, общий бакет реплик и квота на один воркспейс по-прежнему не входят в план.

Проверено без живого RustFS: старый объект без строки снимается, молодой, живой и чужой ключ остаются; страницы списка сходятся; допуск незавершённой загрузки гасит расхождение равного размера; строка без объекта считается; ошибка списка не удаляет байты и не несёт `secretKey`; `fs` и реплика проход не начинают; фраза деградации квоты поднимает флаг без секрета.

## 12. Состав на диске оператора

Сервис `rustfs` включён в compose профилем `rustfs`, а не комментарием и не `depends_on` у `luminascreen`. Контейнер работает от uid `10001`; том `rustfs-data` именованный, отдельный bind на хосте не нужен. Порт S3 наружу не публикуется: его видит только сеть compose. Консоль администрирования — `127.0.0.1:9001`. Образ запинен `rustfs/rustfs:1.0.0-beta.10`. `RUSTFS_ACCESS_KEY` / `RUSTFS_SECRET_KEY` задаются контейнеру RustFS и в процесс Herald как ключ данных не попадают. Провижининг читает `RUSTFS_PROVISIONER_*`. После создания пользователя запись и чтение идут его ключом.

Переменные Herald, все необязательные:

| Переменная | Смысл |
|---|---|
| `CONTENT_BACKEND` | `fs` (молча) или `s3` |
| `RUSTFS_ENDPOINT` | внутренний URL, например `http://rustfs:9000` |
| `RUSTFS_REGION` | любое стабильное значение; по умолчанию `us-east-1`, то же при подписи |
| `RUSTFS_ACCESS_KEY` / `RUSTFS_SECRET_KEY` | корень контейнера RustFS. Herald им объекты не читает и не пишет |
| `RUSTFS_BUCKET` | не используется: бакет организации выводится из её id |
| `RUSTFS_PROVISIONER_ACCESS_KEY` / `RUSTFS_PROVISIONER_SECRET_KEY` | только провижининг |
| `RUSTFS_PLATFORM_ACCESS_KEY` / `RUSTFS_PLATFORM_SECRET_KEY` | бакет шаблонов |
| `STORAGE_SEAL_KEY` | обычно не задаётся: файл в `/data/certs` |

`RUSTFS_PUBLIC_ENDPOINT` не вводим, пока нет presign наружу. Если его когда-нибудь добавят, подписывать нужно тем хостом, который видит плеер, иначе `SignatureDoesNotMatch`.

Секреты не класть в репозиторий и в `.env.example` сверх имён переменных.

SQLite остаётся на томе `st-data`. Том RustFS — отдельный. Смерть одного не должна затирать другой: разные volume.

## 13. Проверки, без которых шаг не закрыт

- Загрузка в воркспейс A не видна в списке B и не читается ключом B.
- `org_admin` читает объект A через Herald (дашборд организации), редактор B — нет.
- Плеер без сессии открывает `/uploads/content/<basename>` ролика из своего снимка и получает байты, `Range` отдаёт 206.
- Неизвестный basename — JSON 404, без тела дашборда и без длинного кэша.
- Слайд с картинкой из библиотеки рисуется в песочном iframe (CORS и CORP как сейчас).
- Удаление одной из двух строк, исторически делящих sha256-файл, оставляет вторую читаемой.
- После переноса оба ряда читаются, локальный файл снят только когда оба `storage_key` на месте.
- Отказ тарифа срабатывает до появления объекта в бакете.
- Реплика с `caches-content` получает файл через первичный URL и играет при выключенном первичном процессе то, что уже успела скачать.
- Обрыв между `PutObject` и `INSERT` не оставляет объект без строки дольше цикла уборки, и не оставляет строку без объекта.
- `CONTENT_BACKEND` пустой — тесты и установка ведут себя как до этого плана.

## 14. Риски

| Риск | Что делаем |
|---|---|
| RustFS ещё beta, часть CLI не реализована | Умолчание `fs`. Включать `s3` на копии данных. Версию образа пиновать. Админ-операции проверять на стенде, не по списку подкоманд `rc` |
| Квота молча пропускает запись | Лимит в Herald первичен. Фраза `Bucket quota check degraded to allow` в ответе хранилища пишется в лог и в `/api/status` (`quota_degraded`) |
| Прокси больших роликов грузит процесс Node | Для первой поставки приемлемо: так байты и сейчас читаются с диска тем же процессом. Прямой presign — следующая поставка, отдельным флагом |
| Двойное место на время переноса | Пока оператор не подтвердил удаление локальных копий, байты лежат и на диске, и в бакете. Первый отказ бакета (квота или место) останавливает перенос и пишет ошибку в статус. Свободные байты тома RustFS этот клиент не спрашивает: data API их не отдаёт |
| Реселлер ожидал, что одинаковый ролик в десяти клиентах занимает место один раз | После переноса занимает десять. Это плата за границу удаления и ключей. До шага 4 это нужно сказать явно |
| Утечка `secret_enc` вместе с `STORAGE_SEAL_KEY` | Оба лежат в `/data`. Кто снял том Herald, снимает и печать. Том RustFS отдельно, но с томом Herald атакующий расшифрует ключи. Корень RustFS при этом всё равно не в томе Herald |
| Песочница и нативные плееры не пришлют IAM-ключ | И не должны. Права экрана — capability URL через Herald (§4.2) |

## 15. Что сознательно не входит

- Замена SQLite, плейлистов, устройств и сессий. В RustFS едут только байты библиотеки.
- Шрифты, APK, сертификаты, `proxy-cache`, плагины.
- Выдача оператору доступа в консоль RustFS.
- Анонимный бакет, ACL, Object Lock, версионирование по умолчанию.
- Отдельный Kubernetes Tenant на заказчика.
- Смена URL, которые уже закэшированы панелями.
- Автоматический failover RustFS. Несколько узлов — по инструкции самого RustFS, повышение реплики Herald — по-прежнему вручную (`docs/scale-out-design.md` §7).
